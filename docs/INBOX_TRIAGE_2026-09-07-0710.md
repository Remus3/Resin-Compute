## Section 2 - Property 6, withdrawal detection

**Bucket: applicable-and-not-done.**

Read `scripts/watch_inbox.py` end to end (`_entries`, `survey`,
`unseen_entries`, `_is_seen`) and grepped `tests/test_watch_inbox.py` for
`withdraw|vanish|delet|removed|retract` - no match beyond the word "vanish"
appearing in unrelated docstrings and one assertion about a note being
mislabelled rather than dropped, and one about an unreadable file
contributing its exception class rather than disappearing from a manifest.
Neither is a withdrawal test. `_entries(inbox)` in `scripts/watch_inbox.py`
(line 237) builds its list by walking what is CURRENTLY on disk, and
`unseen_entries` (line 304) is computed as "entries not already in the
seen map" - RC's exact description of the defect: `names - seen`, so a
deletion simply stops appearing in either list, and a payload withdrawn
after being reported once vanishes from view with no signal that it is gone
rather than merely already read.

**Concrete follow-up for the roadmap**, out of this session's write-list
(`scripts/watch_inbox.py` and `tests/test_watch_inbox.py` are not on it):
add a withdrawal arm to `survey()` that diffs the STABLE NAME half of the
seen-map's keys (the key with its digest suffix stripped, e.g. `child.name`
or `child.name + "/"`) against the stable names of entries currently on
disk, and reports any seen name with no current on-disk match as withdrawn,
in a section distinct from "new" and "changed" so an edit and a withdrawal of
the same name are never conflated - RC's own note names this exact
subtlety ("an EDIT and a WITHDRAWAL both move the key once keys carry
digests... strip the digest and compare the stable NAME"). Pair the new
arm with its own regression test plus a non-vacuity arm proving an
UNCHANGED entry does not get reported as withdrawn, per this tree's
own two-guards convention (CLAUDE.md, "Any sweep needs TWO guards").
